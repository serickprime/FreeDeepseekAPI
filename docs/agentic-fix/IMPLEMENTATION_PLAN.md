# Поэтапный план исправления

Не объединять этапы и не переписывать архитектуру целиком. Перед каждым этапом проверить чистоту дерева, после него — показать diff, выполнить назначенные тесты и дождаться подтверждения пользователя.

## Этап 1 — безопасная диагностика исходной ошибки

- Возможные файлы: `server.js`, `client.js`, `lib/api_stream.js`, `lib/security.js`, новый локальный модуль журналирования, `.gitignore`, `tests/unit.test.js`.
- Затрагиваемые функции: `createProxyServer`, `checked`, `complete`, `createProtocolStream().fail`, `safeError`.
- План: записывать исходную ошибку и безопасный корреляционный идентификатор в локальный журнал с редактированием `Authorization`, cookie, token и body. Клиенту возвращать только безопасное сообщение и идентификатор, без upstream-body.
- Риски: утечка секретов в файл или разрастание логов. Журнал не коммитить и ограничить его размер/срок.
- Проверка: unit-тесты редактирования; integration-тест для streaming/non-streaming ошибки; поиск, что token/cookie отсутствуют в клиентском ответе и журнале.
- Откат: отдельный маленький коммит; удалить только новый код журналирования/вызовы, не меняя протоколы.

## Этап 2 — полный явный doctor

- Возможные файлы: `scripts/doctor.js`, `client.js`, `lib/pow.js`, `tests/unit.test.js`, документация.
- Затрагиваемые функции: `loadAuth`, `createRemoteSession`, `completeOnce`, `solvePOW`, `parseStream`.
- План: по явной команде doctor последовательно проверять создание Web-сессии, challenge, загрузку WASM, решение PoW, один малый completion, текст ответа и streaming. Разделить локальные и upstream-ошибки, не печатая секреты.
- Риски: doctor создаёт реальную сессию и расходует запрос. Он не должен вызываться автоматически в unit-тестах или панели без явного действия пользователя.
- Проверка: mock/unit для каждой стадии; ручная проверка с собственным аккаунтом только после согласия пользователя.
- Откат: вернуть только doctor-изменения отдельным коммитом; не трогать auth-файл.

## Этап 3 — строгое и безопасное распознавание tool call

- Возможные файлы: `lib/tool_parser.js`, `server.js`, `lib/api_stream.js`, `tests/unit.test.js`.
- Затрагиваемые функции: `toolPrompt`, `parseToolCall`, `toOpenAI`, `toAnthropic`, `toResponses`, `createProtocolStream().finish`.
- План: принимать только явно выделенный полный конверт из разрешённого канала ответа; никогда не извлекать вызов из произвольного reasoning и не считать пример JSON вызовом. Разрешать лишь tools, присланные текущим клиентом, проверять имя, схему/тип аргументов и ограничение размера. Bridge только возвращает описание, но ничего не исполняет.
- Риски: чрезмерная строгость снизит долю распознанных вызовов; чрезмерная либеральность превратит текст в ложный вызов.
- Проверка: unit-факторы для неизвестного имени, обрезанного/слишком большого JSON, обычного JSON в тексте, разрешённого вызова и streaming.
- Откат: отдельный коммит parser/adapter; оставить исходную строгую политику, если новая не проходит фикстуры.

## Этап 4 — один безопасный повторный запрос

- Возможные файлы: `server.js`, `client.js`, `lib/tool_parser.js`, `lib/session.js`, `tests/unit.test.js`.
- Затрагиваемые функции: обработчик completion в `createProxyServer`, `complete`/`completeOnce`, `toolPrompt`.
- План: только когда клиент передал tools и первый ответ содержит рассуждение о действии, но не содержит валидного вызова, сделать не более одного дополнительного запроса. Второй prompt должен требовать либо единственный строгий разрешённый JSON tool call, либо финальный текст. Счётчик попыток передавать явно; бесконечный цикл запрещён.
- Риски: дополнительные расходы/лимиты, повторный контекст в удалённой сессии, ложный повтор для обычного ответа.
- Проверка: unit и integration с mock-ответами «reasoning без call → call», «reasoning без call → финальный текст», «две неудачи → остановка».
- Откат: удалить только retry-ветку; этап 3 остаётся независимо полезным.

## Этап 5 — полный цикл tool calling у клиента

- Возможные файлы: `scripts/live_agentic_smoke_tests.mjs`, `tests/unit.test.js`, возможно `server.js`/адаптеры, README после успеха.
- Затрагиваемые функции: `normalize`, `anthropicMessageText`, `toOpenAI`, `toAnthropic`, `toResponses`, streaming `finish`.
- План: проверить цепочку: модель запрашивает разрешённый инструмент → Claude Code/OpenCode исполняет его сам → результат приходит следующим сообщением → модель продолжает ответ. Отдельно подтвердить, что Bridge не запускает shell, MCP или файл-инструменты.
- Риски: live-проверка зависит от аккаунта, внешнего API и установленных CLI; нельзя выполнять без согласия пользователя.
- Проверка: изолированные integration-фикстуры всегда; ручные Claude/OpenCode live smoke-тесты только после явного согласия.
- Откат: тесты отдельным коммитом; при изменениях протокола откатывать только их, не удаляя защиту parser.

## Этап 6 — разделение сессий клиентов

- Возможные файлы: `server.js`, `lib/session.js`, `client.js`, `tests/unit.test.js`, документация.
- Затрагиваемые функции: выбор `sessionKey` в `createProxyServer`, `SessionStore.get/reset/list`.
- План: определить стабильный приоритет идентификаторов (явный `x-agent-session`, совместимый user-идентификатор клиента, безопасный fallback на процесс/подключение). Не использовать общий `default` для разных процессов и не менять явные существующие ключи.
- Риски: потеря продолжения диалога после обновления или несовместимость клиентов без `user`.
- Проверка: две параллельные сессии с разными ключами; повторный запрос каждого клиента сохраняет свою цепочку; регрессия существующего `x-agent-session`.
- Откат: отдельный migration-free коммит; вернуть старую стратегию ключа при нарушении совместимости.

## Этап 7 — count_tokens после проверки требований Claude Code

- Возможные файлы: `server.js`, новый адаптер подсчёта/заглушка, `tests/unit.test.js`, `README.md`.
- Затрагиваемые функции: маршрутизация `createProxyServer`, Anthropic-совместимое кодирование ошибки/ответа.
- План: сначала зафиксировать фактический путь и ожидаемый контракт конкретной версии Claude Code. Затем реализовать корректный подсчёт либо явно безопасную совместимую заглушку; не выдавать оценку за точное число токенов.
- Риски: неверный контракт может сломать discovery или лимиты клиента.
- Проверка: contract-test запроса, smoke Claude Code и негативный тест неизвестного пути.
- Откат: отдельный endpoint-коммит без изменений completion-маршрутов.

## Этап 8 — обновление пользовательской документации

- Возможные файлы: `README.md`, `PROJECT_STATUS.md`, `NEXT_STEP_PROMPT.md`, `docs/agentic-fix/*`.
- Затрагиваемые функции: нет; описываются только подтверждённые интерфейсы и ограничения.
- План: документировать реальные результаты после всех успешных тестов: поддерживаемые протоколы, ограничения tool calling, необходимость собственного аккаунта и порядок диагностики.
- Риски: преждевременные обещания полной совместимости Claude/OpenCode/MCP.
- Проверка: сверка README с тестами и фактическими маршрутами; `git diff --check`.
- Откат: отдельный docs-коммит.
