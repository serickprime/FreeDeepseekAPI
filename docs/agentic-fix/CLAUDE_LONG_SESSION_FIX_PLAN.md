# План исправления Claude Code после длинной сессии и recap

Дата подготовки: 2026-07-22.

Базовая версия: `main` на merge-коммите `4b88d3958dc98ec071485f43536ea25a87fdbdf0`.

Рабочая ветка: `fix/claude-long-session-tools`.

## Цель

Сделать tool calling устойчивым в длинных Claude Code сессиях, после recap/compaction и после смены пользовательской задачи, не ослабляя строгую проверку инструментов и не создавая бесконечные model retries.

Bridge по-прежнему не должен выполнять инструменты. Он только преобразует допустимый tool call в формат клиента и принимает последующий tool result.

## Наблюдаемая проблема

В реальном интерактивном Claude Code сеансе:

1. `Write` создал файл и вернул результат.
2. `Grep` был вызван как настоящий инструмент.
3. После накопления контекста появился `recap`.
4. Модель несколько раз повторяла reasoning о намерении прочитать и обновить одни и те же компоненты.
5. Новое указание пользователя о кабине космического корабля было отложено моделью как «отдельная задача», хотя пользователь явно сменил приоритет.
6. В конце модель вывела строгий объект:

   ```json
   {"tool_call":{"name":"Read","arguments":{"file_path":"<test-project>\\src\\components\\scene\\CameraRig.tsx"}}}
   ```

   Объект был показан как обычный текст и не превратился в настоящий `Read`.

Содержимое пользовательского проекта, реальные локальные пути, prompt и результаты файлов в диагностические журналы добавлять нельзя. Путь в примере намеренно обезличен.

## Что подтверждено

- Основной tool pipeline не сломан полностью: настоящие `Write` и `Grep` выполнялись.
- `parseToolCallFromOutput()` принимает строгий JSON из всего `content` либо из всего `reasoning` при пустом `content` только для имени из `allowedTools`.
- `allowedTools` строится из `tools` текущего нормализованного HTTP-запроса и не сохраняется как capability catalog сессии.
- При наличии tools streaming буферизуется, поэтому промежуточный reasoning не должен показываться клиенту до решения о tool call.
- Reasoning-only коррекция выполняется максимум один раз.
- Точное повторение выполненного tool call получает максимум одну отдельную коррекцию.
- Tool result continuation сохраняет call id и ту же удалённую сессию.
- Для обычных ходов Bridge преобразует весь transcript клиента в prompt и одновременно продолжает stateful DeepSeek-сессию через `parent_message_id`.
- `SessionStore.history` сохраняется, но не участвует в rollover/recovery.
- Claude Code 2.1.216 ранее успешно выполнил два последовательных `Read`; установленная версия теперь 2.1.217.

## Что пока является гипотезой

- Claude Code 2.1.217 после recap может перестать повторять `tools` либо изменить их форму.
- Claude Code мог прислать запрос без tools из-за режима/permissions, а не из-за recap.
- DeepSeek мог вернуть строгий JSON в обычном `content`, когда `allowedTools` был пуст.
- Повторная передача старого transcript поверх stateful DeepSeek-сессии могла закрепить предыдущую задачу и ослабить новое указание.
- Сжатая история клиента могла перестать быть префиксом предыдущего transcript, но Bridge сейчас это не распознаёт.

Ни одна гипотеза не должна становиться основой исправления без воспроизводящего теста или безопасного контрактного probe.

## Инварианты безопасности

- Не выполнять tool call внутри Bridge.
- Не извлекать JSON из prose, Markdown и reasoning-плана.
- Не принимать неизвестный tool.
- Не переиспользовать старое разрешение инструмента без доказанного контракта и теста отзыва permission.
- Не журналировать prompt, reasoning, tool arguments, tool result, содержимое файлов, token, cookie, authorization и auth JSON.
- Не увеличивать corrective retries выше явно ограниченного числа.
- Не создавать общую сессию `default`.
- Не смешивать разные `x-agent-session`, `metadata.user_id`, `user` и call id.
- Не запускать реальные команды, Chrome, DeepSeek или CLI в обычных offline-тестах.

## Этап 1. Безопасная диагностика и регрессионный тест

Цель: доказать, какие capabilities видит Bridge в проблемном запросе.

Допустимые изменения:

- `server.js`;
- новый небольшой модуль безопасной диагностики в `lib/`;
- `tests/unit.test.js`.

Нужно добавить opt-in журнал, например через `BRIDGE_DIAGNOSTICS=1`. Для каждого запроса разрешены только:

- локальный request id;
- API kind/route;
- model;
- `stream: true/false`;
- количество tools;
- нормализованные разрешённые имена tools;
- источник сессии без исходного пользовательского идентификатора;
- количество tool results и наличие известных call id без самих результатов;
- решение: parsed tool, reasoning retry, repeated-tool correction, final text или rejected envelope.

Журнал не должен менять API и не должен падать при необычных данных.

Offline-регрессия должна моделировать два или три HTTP-запроса через реальный `createProxyServer` и mock `completeImpl`:

1. Первый запрос содержит `Read` и получает настоящий tool call.
2. Следующий запрос продолжает ту же клиентскую сессию, но имитирует recap и отсутствие/изменение tools.
3. Mock возвращает строгий JSON `Read`.
4. Bridge не выполняет и не разрешает вызов без актуального разрешения.
5. Журнал точно показывает `tool_count: 0` или результат нормализации, не раскрывая содержимое.

Проверка этапа:

```powershell
git diff --check
node --check server.js
node --check tests/unit.test.js
npm.cmd test
```

После этапа остановиться и показать пользователю diff. Не переходить к capability cache.

## Этап 2. Локальный контрактный probe Claude Code 2.1.217

Цель: выяснить фактический HTTP-контракт без DeepSeek.

Разрешён один безопасный неинтерактивный запуск Claude Code против временного localhost mock-сервера после согласия пользователя. Probe должен фиксировать:

- метод и маршрут;
- наличие `tools` и только их имена;
- форму tool definitions;
- меняется ли список после tool result;
- что происходит после искусственного длинного transcript/compaction, если это можно воспроизвести без внешней сети.

Нельзя сохранять authorization, полный prompt, system, содержимое файлов и пользовательские данные. Временные файлы и сервер не добавлять в Git.

Результат этапа оформить отдельным документом. Если Claude всегда передаёт tools, capability cache не нужен.

## Этап 3. Безопасная совместимость capabilities

Реализация зависит от этапа 2.

Предпочтительный порядок решений:

1. Поддержать подтверждённую новую форму `tools`, если Claude 2.1.217 действительно изменил контракт.
2. Если tools намеренно отсутствуют, вернуть понятную безопасную ошибку вместо сырого JSON.
3. Capability cache допустим только если контракт подтверждает временное опущение неизменных tools. Он должен иметь TTL, лимит размера, привязку к стабильной сессии и очистку при reset.
4. Явное новое пустое/ограниченное разрешение должно отзывать старые tools. Нельзя объединять каталоги по принципу «всё, что когда-либо было разрешено».

Обязательные тесты:

- неизвестный tool отклоняется;
- отозванный tool отклоняется;
- новый ограниченный список заменяет старый;
- разные сессии не делят capabilities;
- анонимные запросы не получают чужой каталог;
- TTL и размер ограничены;
- строгий JSON без разрешения не показывается как успешный инструмент.

## Этап 4. Единая стратегия контекста и recap

Нужно прекратить повторную отправку полного старого transcript поверх уже содержащей его stateful DeepSeek-сессии.

Предлагаемая стратегия:

- хранить bounded fingerprints нормализованных сообщений, а не полное секретное содержимое для сравнения;
- если новый transcript продолжает предыдущий префикс, отправлять только новые сообщения;
- tool result continuation по-прежнему отправляет только текущие подтверждённые results;
- если transcript сокращён, заменён или не является продолжением после recap, создать новую удалённую сессию и отправить актуальный компактный transcript один раз;
- при rollover сохранить актуальную пользовательскую задачу и последние связанные tool results;
- не добавлять скрытый reasoning модели в восстановленный контекст;
- ограничить общий byte budget, глубину истории и число сессий.

Нужно отдельно проверить, что новая пользовательская команда после смены направления имеет приоритет и старый план не дублируется.

## Этап 5. Recovery и параллельность

- Восстанавливать контекст после retryable 5xx, timeout и истечения удалённой сессии.
- Не отправлять один голый tool result в новую пустую DeepSeek-сессию.
- Сериализовать изменения `parentMessageId` внутри одного явного session key или доказать отсутствие гонки тестом.
- Прерывать upstream fetch при отключении клиента.
- Ограничить размер накопленного upstream content/reasoning.

## Этап 6. Полная offline-проверка

Минимум:

- OpenAI, Anthropic и Responses обычные ответы и streaming;
- reasoning-only retry и его предел;
- строгий tool parser;
- tool result continuation;
- два последовательных разных инструмента;
- тот же инструмент с другими arguments;
- точный повтор и только одна коррекция;
- recap с tools и без tools;
- смена задачи;
- rollover после потери upstream-сессии;
- две параллельные явные сессии;
- отсутствие prompt и секретов в диагностике;
- отсутствие регрессий всех существующих 101 тестов.

## Этап 7. Live-проверка после согласия

Порядок:

1. `npm run doctor` один раз.
2. `npm run test:live` один раз.
3. Claude Code текущей версии: два чтения, tool result после каждого, затем смена задачи в той же сессии.
4. Отдельный длинный тест/recap только в временной папке и только read-only tools.
5. OpenCode после устранения его локальной ошибки запуска.
6. Проверка разделения двух сессий.

Не повторять live-команды автоматически при ошибке.

## Этап 8. Документация, PR и merge

После успешных тестов:

- обновить README без обещания полной совместимости будущих версий;
- записать проверенные версии CLI;
- создать итоговый отчёт;
- проверить diff на секреты;
- сделать маленькие тематические коммиты;
- push и PR выполнять только по отдельному разрешению пользователя;
- `main` не менять до успешного review и явного разрешения на merge.

## Первый безопасный шаг следующего агента

Выполнить только этап 1: opt-in безопасная диагностика и offline-регрессия. Не реализовывать capability cache, transcript delta и rollover одновременно. После тестов остановиться и дождаться решения пользователя.
