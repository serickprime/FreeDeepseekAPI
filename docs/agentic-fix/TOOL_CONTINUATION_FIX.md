# Исправление повторного tool call после tool result

Дата проверки: 2026-07-22. Ветка: `fix/agentic-tool-loop`.

Проверенная исходная точка: `511cea4ce03140f7a82a4d8214d02c11d9238c27`.

## Подтверждённая причина

До исправления Bridge использовал ту же удалённую DeepSeek-сессию и сохранял `parentMessageId`, но второй HTTP-запрос заново превращал весь клиентский диалог в один upstream prompt. В него повторно попадали исходная пользовательская задача, уже возвращённый assistant tool call и новый tool result. Затем к этому тексту снова добавлялась обычная инструкция первого запроса `TOOL REQUEST SYSTEM`.

Регрессионный HTTP-тест с реальным `createProxyServer` и mock `completeImpl` подтвердил это поведение до изменения серверной логики. DeepSeek одновременно видел сохранённый контекст удалённой сессии и повторную текстовую копию незавершённого вызова, поэтому мог решить, что инструмент `echo` ещё не выполнен.

## Как изменён continuation prompt

Для известного call id Bridge продолжает использовать ту же локальную и удалённую сессию с сохранённым `parentMessageId`, но больше не отправляет старый клиентский диалог повторно. В новый upstream prompt попадают только ещё не обработанные результаты инструментов текущего продолжения:

- имя инструмента;
- call id;
- фактический результат клиента.

Отдельная continuation-инструкция явно сообщает модели, что клиент уже выполнил инструмент и результат является настоящим. Она требует финальный ответ либо один другой необходимый строгий JSON tool call. Обычный prompt первого запроса не используется без изменений. Уже обработанные call id удаляются из временного сопоставления, поэтому старые результаты не дублируются в следующем ходе.

Bridge по-прежнему не выполняет инструменты самостоятельно.

## Защита от точного повторения

Добавлена одна ограниченная корректирующая попытка. Она срабатывает только когда после настоящего результата модель повторяет то же безопасно сохранённое имя инструмента с теми же JSON arguments. Порядок ключей JSON не влияет на сравнение.

Коррекция:

- выполняется максимум один раз;
- использует ту же удалённую сессию;
- работает в режиме без reasoning и поиска;
- не показывает промежуточный ответ или служебный prompt клиенту;
- разрешает другой инструмент и тот же инструмент с другими arguments;
- после второго точного повтора завершает ответ безопасным сообщением без третьей попытки.

## Оставшиеся ограничения

- Проект зависит от внутреннего DeepSeek Web API, который может измениться.
- Временные связи call id хранятся только в памяти процесса.
- Защита блокирует только точный повтор известного name + arguments; новый инструмент или другие arguments передаются клиенту как обычно.
- После этого исправления ещё требуется отдельная реальная проверка Claude Code и OpenCode. Эта проверка не входит в текущий live smoke-тест и не выполнена в рамках данного исправления.
