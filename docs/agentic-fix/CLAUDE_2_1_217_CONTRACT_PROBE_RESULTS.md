# Результаты локального contract probe Claude Code 2.1.217

Дата проверки: 2026-07-22.

## Область проверки

Проверка выполнена локально, без DeepSeek и без запуска Bridge. Claude Code подключался к временному HTTP mock-серверу на `127.0.0.1` со случайным свободным портом. Сервер не перенаправлял запросы во внешнюю сеть. Временная рабочая папка содержала только два файла с синтетическими маркерами и была удалена после завершения.

Фактическая версия клиента: Claude Code 2.1.217.

Безопасная форма команды:

```powershell
claude.cmd --print --safe-mode --strict-mcp-config --no-session-persistence --disable-slash-commands --tools Read --allowedTools Read --disallowedTools Write,Edit,Bash,NotebookEdit,WebFetch,WebSearch --output-format text --model sonnet [synthetic read-only task]
```

В дочернее окружение передавались только локальный `ANTHROPIC_BASE_URL`, фиктивный `ANTHROPIC_AUTH_TOKEN`, необходимые Windows-переменные и подтверждённые локальной сборкой переключатели отключения необязательного трафика, телеметрии и обновлений. Настоящие credentials DeepSeek не использовались.

## Подтверждённый HTTP-контракт

В базовом сценарии клиент выполнил три потоковых `POST /v1/messages`. Других маршрутов он не запросил.

Первый запрос:

- `tools` присутствует и имеет тип array;
- передан один инструмент `Read`;
- объект инструмента содержит ключи `name`, `description` и `input_schema`;
- `system` и `messages` передаются массивами;
- клиент запросил streaming;
- алиас `sonnet` был разрешён клиентом в модель `claude-sonnet-5`.

После первого `tool_result`:

- `tools` по-прежнему присутствует;
- число и имя инструментов не изменились;
- полная форма массива tools совпала с первым запросом;
- messages содержат связанный `tool_use` и следующий за ним `tool_result`;
- первый синтетический маркер действительно находился в результате чтения; проверка выполнялась только в памяти.

После второго `tool_result`:

- `tools` снова присутствует;
- число, имя и полная форма tools остались неизменными;
- messages содержат оба `tool_use` и оба `tool_result`;
- второй результат связан со вторым вызовом;
- второй синтетический маркер действительно находился в результате чтения; проверка выполнялась только в памяти.

После этого mock вернул обычный text block, Claude Code завершился с кодом `0`. Всего получено ровно три запроса к Messages API, бесконечного цикла не возникло.

## Content blocks

Наблюдалась следующая безопасная последовательность типов блоков:

1. Первый запрос: `text`, `text`.
2. После первого чтения: `text`, `text`, `tool_use`, `tool_result`.
3. После второго чтения: `text`, `text`, `tool_use`, `tool_result`, `tool_use`, `tool_result`.

Текст блоков, arguments, результаты инструментов и полные идентификаторы не сохранялись.

## Count tokens

`POST /v1/messages/count_tokens` в базовом сценарии не вызывался. Mock поддерживает этот маршрут и возвращает совместимый локальный ответ `{"input_tokens":100}`, но фактического запроса от Claude Code в этом запуске не было.

## Compaction и recap

Локальная нативная сборка подтверждает наличие:

- `CLAUDE_CODE_AUTO_COMPACT_WINDOW`;
- автоматической compaction и её отключения;
- pre/post-compaction событий;
- внутренней функции `compactTranscriptForTesting`;
- маршрута `/v1/messages/count_tokens`.

Локальные строки конфигурации показывают, что пользовательский порог `CLAUDE_CODE_AUTO_COMPACT_WINDOW` принимает значения от 100k токенов. CLI-справка не предоставляет безопасного детерминированного тестового флага, который гарантированно вызвал бы compaction в пределах 20 коротких read-only запросов. Внутренняя функция тестирования не является доступным CLI-контрактом.

Поэтому отдельный compaction probe намеренно не запускался. Реальная compaction не подтверждена, а наличие и форма `tools` после неё остаются неизвестными. Успешная compaction не имитировалась.

## Подтверждённые факты и гипотезы

Подтверждено:

- Claude Code 2.1.217 не удаляет `tools` сразу после первого или второго `tool_result`;
- обычный двухшаговый read-only tool loop сохраняет неизменный формат tools;
- `tool_use` и `tool_result` передаются в messages с корректной связью;
- в базовом сценарии `count_tokens` не нужен клиенту;
- два реальных локальных чтения были выполнены, результаты дошли до следующего модельного запроса.

Опровергнута гипотеза, что версия 2.1.217 всегда перестаёт передавать tools сразу после первого tool result.

Не подтверждены:

- удаление или изменение tools именно после настоящей compaction/recap;
- влияние длинной stateful-сессии DeepSeek на старый контекст;
- причина ранее наблюдавшегося строгого JSON `Read`, показанного как обычный текст;
- необходимость capability cache или автоматического восстановления старого списка tools.

## Вывод для следующего этапа

На основании этого probe менять Bridge и автоматически переиспользовать старые tools нельзя: обычный контракт Claude Code 2.1.217 корректно сохраняет tools. Следующий безопасный этап — один контролируемый live-сеанс с `BRIDGE_TOOL_DIAGNOSTICS=1`, где пользователь воспроизводит настоящую длинную сессию/recap, а журнал сравнивает только разрешённые признаки до и после события. До получения этих данных нельзя добавлять capability cache, новые retries или rollover.
